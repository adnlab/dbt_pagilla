To give your students practical, industry-standard wisdom, you can structure the best practices section of your lecture into four distinct themes: Materializations, Coding & Style, Data Quality & Testing, and Performance Optimization.

1. Model Selection & Materializations
Choosing the right materialization is critical for balancing database performance and storage costs.
DO select the appropriate strategy based on your transformation complexity:
Views: Best for minor transformations, such as column selection, renaming, and basic filtering.Tables: Best for long-running, CPU-intensive transformations or heavy computations to ensure dashboards do not have to wait for on-the-fly execution.Incremental Models: Best for massive transactional datasets to optimize processing time by picking up and merging only the new data (delta).Ephemeral Models (CTEs): Best as virtual, reusable helpers for simple to intermediate data preparation where you do not want to clutter the database with physical tables.Materialized Views: Best for pre-computing and caching complex aggregations and joins on tables that update frequently.DO keep Seeds small: Only use seeds to load tiny, static lookup CSV files (like postal codes or country mapping datasets).DON'T use Seeds for raw data integration: dbt is not designed to replace high-volume data ingestion or ETL pipelines.DON'T turn everything into a View: Overusing views causes downstream queries and dashboards to perform poorly because the underlying queries must rebuild on every single refresh.

2. Coding Style & Templating (Jinja)
Jinja brings dynamic programming into SQL, but it requires strict guardrails.
DO use referencing functions consistently: Always use {{ ref() }} and {{ source() }} instead of hardcoding database table paths. This is how dbt generates the Directed Acyclic Graph (DAG) and safely handles switching between development and production environments.DO build reusable macros: Abstract highly repetitive logic (such as custom database logging or mathematical models) into dry, reusable macros.DO override schemas with custom macros: Since appending custom schema names to your default target schema is dbt's default behavior, implement a custom generate_schema_name macro to cleanly replace the target schema for cleaner workspace organization.DO apply whitespace control: Use the dash indicator in your Jinja delimiters (e.g., {{- or -%}) to clean up compile-time spaces and make generated SQL highly readable.DON'T nest curly braces: Never write nested curlies (e.g., {{ {{ var_a }} }}) as this breaks the dbt compiler.

3. Data Quality & Testing
A data product is only as good as the trust it commands.
DO implement out-of-the-box generic tests: Ensure that your primary keys are validated with unique and not_null constraints, and use accepted_values or relationships tests to maintain referential integrity.DO write singular tests for complex logic: Use custom SQL validation queries inside your tests/ directory to look for data anomalies (e.g., ensuring a student's grade is within bounds). Design the test query to fail if it returns any records.DO select the right snapshot strategy: Use the timestamp strategy for tracking historical changes (SCD Type 2) if your source table has an updated timestamp column. Only use the computationally heavier check strategy (which scans all or configured columns) if a timestamp is entirely missing from your source.DON'T run untested code in production CI/CD: Establish a rule to clone your incremental models as the very first step of your CI jobs, ensuring you can test new changes safely against existing datasets.

4. Performance Optimization
DO leverage partitioned sources: When using materialized views, make sure the underlying source tables are partitioned to dramatically reduce refresh costs and processing time.DO align refresh intervals: Sync your materialized view's refresh_interval_minutes to match the data loading cycles of your ingestion pipeline (e.g., if raw data lands every 2 hours, set the refresh interval to 180 minutes to keep a safe buffer).DO fine-tune static analysis: Configure strict static analysis checks during local development to catch compile-time issues immediately, but use a baseline configuration in your CI/CD deployment runs to keep execution speeds high.
